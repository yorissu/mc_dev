
open questions for future reworks
=================================

questions that came up while finishing the python implementation and porting
it to c. nothing here blocks anything: each one lists what both
implementations do today, so the answer only decides whether to change it.


the language
------------

1. unicode in identifiers. names are ascii letters, digits and '_' today;
   other characters are E0101. allow unicode letters (as python and c23 do)? - NO

2. format specifiers. print and println know '{}', '{{' and '}}' only. add
   '{:x}', '{:08.3}', '{:>10}' and similar, checked at compile time like the
   placeholders already are? - YES

3. attributes on statements. '[wrap]' and '[uninit]' work on lets,
   assignments and expression statements. should any statement (a block, a
   loop) take them, so '[wrap]' can cover a whole loop? - I suppose, yes?

4. field-level 'mut'. a field marked 'mut' can be written through a non-mut
   variable of the struct? today a field is writable when both the variable
   and the field allow it. is that the intended meaning, or should 'mut' on a
   field only document intent? - We will most likely rework the mut soon, so dont worry about it now

5. runtime overflow. arithmetic on values known at compile time warns
   (W0701) unless '[wrap]'; at run time it always wraps silently. should
   overflow at run time stop the program (in a debug mode), as the warning
   suggests it is a mistake? - No. Runtime is user's land, not compiler's.

6. empty slices are null. 'slice == null' is true for every empty slice, not
   only for the null slice (the machine compares the length). intended? - I dont know. what about go or rust or odin, do they allow empty slices? and differentiate beween null slices and empty slices?

7. printing u8 arrays and slices strips one trailing NUL (so "text"c prints
   as text). intended for slices too, or only for arrays of 'c' literals? - Only for c strings, so 'c' literals.

8. extern functions as values. a '[builtin]' function can be used as a value,
   an '[extern]' function cannot: the checker accepts it, then the compiler
   stops with E0602 asking to wrap it in a function. allow it (or reject it
   in the checker with a proper diagnostic)? - I suppose extern function should be allowed to be used as a value. it is supposed to have a definition still, which tells the compiler all the info about the types, parameters etc. so it should be allowed.

9. main's arguments. main takes no parameters; should it receive the command
   line ('main :: (arguments: [][]u8) -> int')? - YES


the standard library
--------------------

10. math. there is no sqrt, sin, pow, floor... add a 'math' module as
    natives ('[extern = "mc_sqrt"]')? the c machine makes this a one-line
    table entry per function (source/vm_builtins.c).

11. alloc with a negative count. alloc(-3) makes a slice of length -3, and
    realloc with a negative count keeps all but the last elements (python
    slicing). both implementations do the same, but it should probably be a
    runtime error. make it one?

12. allocation size. the c machine refuses to allocate more than 2^28
    elements at once (runtime error); python tries and may run out of
    memory. keep a limit? make it an option?

13. leaks. memory from alloc that is never freed is collected silently when
    unreachable. report unfreed allocations at exit (an option of 'run')?

ANSWER: I want to implement the stdlib myself. I think that for stuff like math, functions shall be externs, rather than builtins. maybe it should be same with memory and other functions. Do we even need builtin anymore then? we can just extern malloc and have the definition have out types, no?


the tools
---------

14. json diagnostics. besides '--format human' and '--format short', add
    '--format json' for editors and other tools?

15. limits. the compile-time evaluator stops after 1,000,000 steps (E0705);
    the machine stops after 10,000 nested calls. make them options? the c
    'run' has '--limit <n>' for instructions (the python 'run' got it too,
    for the differential tests). - yes, should be options.

16. the bytecode file is json (readable, shared by both implementations). a
    binary format would load faster. worth it? - Yes. I actually want the program to be as fast as possible.

17. windows. the c port builds with gcc/clang (linux, wsl, macos): it uses
    __int128 and a few posix calls (isatty; the tests use mkdtemp and
    open_memstream). support msvc too? - yes, compiler/interpretter should be cross platform.

18. python parity. the c implementation reports runtime errors more
    compactly (repeated calls collapsed, advice added), prints the
    'N error(s), M warning(s)' line for every command, and has 'explain',
    '--werror', '--stats', '--version'. port these back to python, or let
    the python implementation stay the plain reference? - No, we drop python soon.

19. step-limit positions. where E0705 points depends on how many values the
    checker probed before (probes count as steps). both implementations
    agree, but the position is somewhat arbitrary. report the loop or call
    that ran too long instead? - Sure


changes made to the python implementation during the port
---------------------------------------------------------

- diag: '--format short' (one line per diagnostic).
- cli: '--limit <n>' for 'run'.
- evaluate: struct constants keep their fields in layout order.
- checker: positional entries in a struct literal no longer produce a second
  confusing error ('has no field None').


decided during the rework
=========================

decisions made while doing the rework (rework_prompt.md) without asking.
each one is easy to revisit.

- order of the work: the c-like memory layout (task 2) was done before the
  plugins (task 1). the plugin api hands plugins pointers to the bytes of
  slices, which only exist once the machine stores data the way c does;
  doing the plugins first would have needed a throwaway translation layer.
  the binary '.mcb' format (task 3) came with the same change, since the
  json format would have had to change anyway.
- slices are 16 bytes (sizeof([]T) stays 16): a block handle (table index,
  29-bit generation, read-only bit, kind) and a word with the byte offset
  (32 bits) and the length (32 bits). so one slice covers at most 4 GiB and
  2^32 - 1 elements; 'alloc' refuses more than 4 GiB at once (besides the
  2^28 element cap) with the old message. a generation wraps after 2^29
  reuses of the same table entry, after which a very old dangling slice
  could pass the check (practically never).
- no garbage collector: frames are freed when their call returns, heap
  blocks by 'free' and 'realloc', and everything else when the program
  ends. memory that is never freed is not reclaimed while the program runs
  (like c). '--stats' now prints the number of heap allocations instead of
  collections.
- a temporary whose address is needed (a slice of a call's result, a
  literal passed for a slice parameter, '&5') lives in its own slot of the
  frame, like a c compound literal: in a loop, every iteration reuses the
  slot. before, every evaluation made a new object.
- the operand stack holds f32 values as doubles (exact) and rounds after
  each operation, as before, so results are unchanged.
- 'for i in a..=b' where b is the largest value of a 64-bit type: the
  stop value wraps, so the loop runs zero times (before: forever, in
  practice).
- the bytecode changed completely (byte offsets instead of slots, typed
  loads and stores, intrinsics instead of builtins and natives); dis
  listings and instruction counts (--limit, --stats) differ from before.
- function values of builtins print as before ('<function alloc>', without
  the module).
- loading a module verifies it (jump targets, operand stack depths,
  offsets into frames and stack values, call and return sizes) and every
  access through a slice or location is bounds-checked against its block,
  so a damaged '.mcb' file is refused or stopped with a message instead of
  crashing.
- plugins: the qualified name of a '[plugin]' function is the dotted name
  its module was first imported by ('memory.alloc', 'math.sqrt'), and
  'main' for the entry file ('main.f'). a file outside the standard
  library gets the name of its import ('import tools.math' gives
  'tools.math.sqrt').
- plugins are loaded from $MC_PLUGINS (a list of files and directories,
  separated by ':' or ';' on windows), then from '--plugin <file>' and
  '--plugin-dir <dir>' in the order given; a directory loads every file
  with the platform's library ending (.so, .dylib, .dll). two plugins that
  provide the same function are an error (E0603) rather than one winning.
- the built-in plugin is named 'std'. '[plugin = "std"]' works like any
  other plugin name.
- new diagnostic codes: E0416 (no plugin provides a function that is used;
  also when a '.mcb' file is run and a plugin is missing), E0531 and W0531
  (errors and warnings a plugin's check reports without a code of its
  own), E0603 (a plugin cannot be loaded). a check may report with any
  existing code; the 'std' check of formats uses E0530.
- a '[plugin]' function that is declared but never used needs no plugin.
- a plugin function's check runs only on calls whose arguments have no
  errors, and only on direct calls (not through function values).
- plugin functions can be used as values (apply(math.sqrt, 2.0)); variadic
  ones cannot (as before for builtins: E0529).
- the plugin api gives a plugin the bytes of slices and of struct and
  array arguments (c layout), and decodes slices and function values
  stored in memory for it ('mc_plugin_slice_at', 'mc_plugin_function_name_at').
  calling an mc function value from a plugin is not in this version of
  the api.
- 'mono' marks plugin functions with ' [plugin]' (was ' [builtin]').
- format specifiers: '{:.n}' without a type is 'g' with n significant
  digits (c's %g); 'e', 'E' and 'f' without a precision use 6 digits (like
  c and python); 'g' without a precision is today's shortest text. '#'
  works with 'x', 'X', 'o', 'b' only ('0X' for 'X'); negative numbers in
  those bases are written with a minus ('-0xff'). a sign or '0' applies to
  numbers only, a precision to floats only; anything else is E0530 at
  compile time. widths count code points of the text; nan and infinities
  are padded with spaces even with '0'. a width is at most 10000 and a
  precision at most 100.
- trailing NUL: besides "..."c literals, constants made from them and
  slices of either (the rule asked for), a variable that is not 'mut' and
  starts as a c string counts too (let text = "hi"c; println("{}", text)
  still prints 'hi'). a c string inside a struct or an array is written
  with its NUL now (before: every u8 array lost one trailing NUL).
- '[wrap]' on a statement (any statement now, a 'return' included) no
  longer reaches into lambdas and local functions declared inside it (that
  is also new for '[wrap]' on 'let', assignments and expressions, which
  used to reach them); '[wrap]' on a function still does. 'break' and
  'continue' take no attributes (E0403).
- 'mc run <file> ...': everything after the file is the program's command
  line (so mc's own options come before the file); '--' ends mc's options
  (for files that start with '-'). 'main' gets the file as given first.
  the command line is read-only constant memory: writing to it is a
  runtime error, and 'free' says it is not memory 'alloc' returned.
